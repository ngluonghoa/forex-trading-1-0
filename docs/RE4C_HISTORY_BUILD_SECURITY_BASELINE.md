# RE4c2 — Reachable Git-history secret scan and build-requirement advisory gate

**Scope:** incremental source-security follow-up after RE4c main `c318a4b4d1abcde9a9eb92fd9c6f20d9990dbcae`. Source of truth remains the native Google Docs Handoff, QA and Release Standard. New gates do not mean signed release, authorized LKG or production security signoff.

## Git history scan (blocking)

- `actions/checkout` has `fetch-depth: 0`; `tools/check_git_history_secrets.py` rejects shallow repositories and enumerates all objects reachable through local refs (`git rev-list --objects --all`). It uses a bounded `cat-file --batch-check`/batch blob read to scan each unique reachable UTF-8 textual blob for the already-defined high-confidence key signatures.
- The scanner reports only object hash prefixes and signature IDs, never matched credential bytes or historical file content. It explicitly reports count of binary/non-UTF8 blobs excluded; aborts on incomplete metadata, oversized content, oversized history, corrupt streams or empty histories. Tests verify deleted-token detection in previous commits, clean history, binary counting and fail-closed empty history.
- **Important limits:** currently reachable locally fetched refs only; not unreachable Git objects, reflog, deleted/unfetched refs, remote caches/forks, platform private secret-scanning or generic high-entropy credentials. Binary blobs are counted but not examined for embedded secrets. A clean result is *not* proof no old credential was ever exposed; any genuinely leaked credential must be rotated/revoked independently.

## Python PEP 517 build dependency advisory gate (blocking)

- `tools/write_build_audit_requirements.py` parses the live `pyproject.toml` via Python 3.11+ standard `tomllib`, validates required `build-system.requires` entries and generates a transient CI-only `.ci-build-requirements.txt`. CI executes `pip-audit --progress-spinner off --requirement .ci-build-requirements.txt` with live advisory lookup; missing or failed resolution blocks the job.
- Original build-system declaration was `setuptools>=70,<80` (an open range). **Negative PR CI 42446881100** independently reported setuptools 79.0.1 with three advisory entries (`PYSEC-2026-3447` twice and `GHSA-xmj3-9gf7-h52w`), with fix versions 83.0.0/84.1.0. Corrective source change pins `setuptools==84.1.0` in `pyproject.toml`, ensuring the PEP 517 declared build backend version is unambiguous. CI must verify that this version is available, passes pip-audit, builds package and preserves all tests and artifact receipts. **Pinning setuptools does not prove an immutable hash-locked isolated build**: no hash-locked transitives, pip version/OS toolchain/runner provenance or cross-host signed attestation are asserted. It does not pin transitive build tools, OS/runner/Actions, project runtime (separately audited by existing RE4c), SHA hashes, wheel/signature provenance, or deliver an SBOM. Freeze toolchain and establish signed cross-host provenance in later RE5.
- Both scanners run in the same existing 3.11/3.12 CI job as unit/negative tests, Ruff, mypy, Bandit, current-tree secret scan, declared runtime pip-audit, pip check and twice-built wheel SHA parity. All new scanner checks must pass without ignores/whitelists. No changes to application data sources, business rule sets, live caches, release/LKG, rollback actions or broker authorization. The only source metadata update is the build-system pinned `setuptools` version; it does not add an application runtime dependency.
